# 官壳的后台启动：窗口为什么总会露一帧（七种做法的实测结论）

记录时间：2026-09-30。调查对象：官方桌面壳（Electron，`D:\Family\dsh-official\DeepSeek Harness.exe`，
内置运行时 0.2.0-rc.1）。结论：**在"不修改目标程序"的前提下无法做到零帧闪烁**，已按用户决定容忍。
本文记录试过什么、各自为什么失败或成功，以及哪些结论是实测而非推理。

---

## 一、问题的形状

「随壁纸启动 DSH」与输入岛的滑槽这两条路是**后台启动**：用户要的是"它跑起来，但别让它的窗口冒出来，
只在我要的时候（托盘、输入岛那枚图标、设置「打开」）才出现"。

壳自己没有隐藏启动的参数（这一点查过它的包，见 `dsh-shell-hidden-start-via-bridge.md`）。

## 二、一次后台启动的实测时间线（毫秒为标记自带）

```
requested          +0ms     trigger=Slider / Automatic
port-answered      +2331ms  端口开始应答（webserver 先监听）
family-windows     +2376ms  count=8 on_screen=0
window-exists-hidden +2376ms 我们已经拿到那个界面窗口的句柄，此时它还不可见
moved-offscreen    +2377ms  整族挪到所有显示器之外（本机 = 虚拟屏右缘 2560 + 64）
bridge-ready       +2640ms  桥就绪（宿主运行时装配完成）
window-visible-at  +2655ms  它第一次可见时的矩形 (2624,0)-(4565,1243) —— **仍在屏幕外**
position-restored  +2712ms  隐藏落地后立刻把位置挪回原处
hide-landed        +2712ms  via=tick，visible-frame 36~71ms
settled            +4707ms  连续 2 秒不在屏上，这一场结束
```

两个关键事实：

* **桥就绪早于壳显示窗口约 55ms**（`bridge-ready +2640` vs 显示 ≈ `+2650`），所以"等宿主状态"确实比盲
  轮询早一个阶段；
* **我们挪走的那个窗口从头到尾没有出现在任何显示器上**——用系统的 `MonitorFromRect(MONITOR_DEFAULTTONULL)`
  判定 `(2624,0)-(4565,1243)` 为"不在任何显示器上"。

## 三、七种做法与各自的结局

| # | 做法 | 实测结局 |
| --- | --- | --- |
| 1 | 事后隐藏：按可执行文件路径把家族可见窗口 `ShowWindow(SW_HIDE)` | 壳随后的显示会把它弄回来（实测 **513ms** 后回到屏幕）；那一帧最坏可见约 80ms |
| 2 | 用桥的就绪作时钟，把 tick 压到 1ms，`EVENT_OBJECT_SHOW` 回调里就地隐藏 | 观测点确实提前了（见上表 +55ms），但那一帧仍有 **31~41ms**——这是"壳画出第一帧 → 我们跨进程按下去 → DWM 合成"的固有往返，与检测速度无关（把枚举移出 tick 后 `sweeps` 从 14 降到 11，帧长反而没变） |
| 3 | 冻结画面遮盖：先 `BitBlt` 截下那块屏幕，再用置顶/不激活/点击穿透的窗口盖上去，让壳"出生在面底下" | 两次失败：第一次被**我自己的守卫**挡掉（要求"那块地方必须是我们的画面"，而用户屏幕上恰好有别的窗口）；收窄守卫后**依然可见** ⇒ 该方向被用户冻结（代码保留、接线注释，见 `client_window::raise_launch_cover` 的 FREEZE 说明） |
| 4 | 挪到屏幕外（只挪我们盯着的那一个窗口） | **机制本身成立**：挪走生效、壳没有把它摆回去、它第一次可见时仍在屏幕外（系统判定）。但用户仍看到轮廓——因为家族里还有**第二个**界面窗口没被挪（`Chrome_WidgetWin_0` 就待在正常位置） |
| 5 | 挪走整个家族（未显示、无属主、非弹出物/辅助窗口的顶层窗口一起挪，逐个记放置状态、按句柄恢复） | 用户仍能看到窗口闪过 |
| 6 | 加 `EVENT_OBJECT_CREATE` 钩子（窗口一创建就挪走）+ 处理"非盯着的那个"窗口的显示事件 | **引入回归**：一个窗口变成两个（一个白的、一个疑似黑框）。已整体撤销（提交 `4ad6b0d`） |
| 7 | 让桥/宿主自己"启动即隐藏" | **不存在这条路**：宿主子进程与 Electron 主进程之间的 IPC 是闭集，插件 API 没有桌面/窗口/托盘服务，壳那侧闭源。详见 `dsh-shell-hidden-start-via-bridge.md` |

## 四、为什么外部干预到不了零

1. **显示时机与位置由应用自己决定**。壳以 `show: false` 创建主窗口，等宿主运行时 ready 之后自己调
   `window.show()`；它还把自己的窗口状态写在 `%APPDATA%\DSH Desktop\main-window-state.json` 里。
   外部能做的最早动作，是"在它显示之前把它挪走/盖住"，而它随时可以再创建、再显示别的窗口。
2. **`STARTUPINFO` 那条捷径对我们不适用**：我们是用 AUMID 激活打包应用（日志原话
   `program=explorer.exe arg=shell:AppsFolder\com.deepseek.dsh`），**没有我们可控的 `STARTUPINFO`**；
   而且壳是 Electron，`STARTF_USEPOSITION` 这类提示本来也常被忽略。
3. **剩下的下限是"显示→隐藏"的一次跨进程往返**：实测 31~71ms，即一到两帧。检测再快也跨不过它。

## 五、现在保留的行为（都不再追求零帧）

* **一场竞速**：每次后台启动只藏一轮，首次藏住 + 2 秒静默（或 45 秒上限）即结束；用户若要过这个窗口，
  本轮立刻让位（**不再反复按回去**——这正是用户最初报的"十几秒一直被按死"）；
* **托盘菜单不被吃掉**：只藏"未显示、无属主、非弹出物/辅助工具类"的顶层窗口（`#32768` 菜单、`#32770`
  对话框、tooltips、`electron_*hostwindow`、输入法全部排除）；
* **整族挪到屏幕外 + 隐藏后立刻归位**：被挪走的那个窗口确实不会再落到任何显示器上，位置也不会漂移
  （归位是在**隐藏状态下**做的，所以看不见；这一点很重要——**不要让隐藏窗口一直待在屏幕外**，否则
  应用会把那个坐标存进自己的窗口状态里）；
* 枚举扫描与 1ms tick 作为兜底，`EVENT_OBJECT_SHOW` 钩子继续挂着。

## 六、若将来还要继续，只剩两条路

1. **向上游要一个 seam**：让宿主运行时把"这次启动请隐藏"转达给壳（先例是目录选择器那条：
   壳通过全局交接把原生能力提供给插件）。DSH 目前**不接受外部 PR**，文档里的路径是 Discussions 加
   `dsh-plugin` 话题；改动要同时落在宿主与闭源的壳两侧，体量中到大。
2. **接受现状**：把后台启动理解为"它会短暂露一帧"，并把这一点写进用户可见的说明里。

## 七、未验证与已知未知

* 第 5 种做法当时挪走了几个窗口，日志里查不到：本地日志有长度上限，开头那几行（含 `moved-offscreen`
  的数量）在我读取时已被截断。后续已把数量并进靠后的 `hide-landed` 标记；
* 用户看到的"窗口闪过"具体是哪一个窗口（我们盯着的那个已被证明不在任何显示器上，所以是别的窗口），
  没有在引入回归之前定位到；
* 第 6 种做法为什么会让窗口变成两个，没有查（选择直接撤销，而不是在未知状态下继续改）。

## 八、补记（2026-09-30 晚）：这条线被"改用 CLI"整体取代

用户提出并确认了一个更简单的路线，它让上面七种做法的努力**全部不再必要**：

**后台不启动 GUI，改跑所选主体的 CLI，用它的 `web` 档案起一个无窗口的 HTTP 宿主。**

| 角色 | 用什么 | 有没有窗口 |
| --- | --- | --- |
| 后台（滑槽切到 harness 时） | **所选主体的 CLI**，`--profile web`，监听 HTTP | **没有**（真正静默） |
| 前台（用户在设置里按「打开」，或点输入岛左侧那个按钮） | 完整的桌面壳 | 有，但这是用户主动要的 |

**为什么这是对的**：闪屏的成因是"要显示一个我们无权控制的窗口"，而这个方案的背景角色**根本不启动那个窗口** —— 问题不是被压制，而是不存在。前七种做法都在试图"事后干预一个已经决定要显示的窗口"，方向本身就受限。

**为什么"选的是谁就用谁"（用户 2026-09-30 拍板）**：不是所有用户都同时装了三种 dsh；纯桌面壳用户没有全局 CLI，而**壳自己就带着一份**：

```
<壳安装目录>\resources\runtime\cli\bin\dsh.cmd          ← 官壳自带的 dsh CLI
<壳安装目录>\resources\runtime\bin\node.cmd
<壳安装目录>\resources\runtime\primary-runtime\dependencies\{node,pnpm,python}
<壳安装目录>\resources\runtime\cli\command-path.ps1       ← 把 CLI 放进 PATH 的脚本
```

于是三种主体各自都有可用的 CLI：桌面壳用它自带的那份；已安装 CLI 用它自己；源码检出用它树里的启动链。
路径要**动态解析**（壳更新会换目录），不要写死。

**已经验证过的前提**（见 `dsh-profiles-ports-and-sessions.md` 与本次实测）：

* 桥能装进 `web` 档案，且实测 `bridge-ready`（今天在本机确认过）；
* 会话与工作区**按 `DSH_HOME` 归属、不按档案隔离**，所以后台的无窗口宿主与前台的桌面壳看到同一批会话，切换是无缝的；
* 官壳自带 CLI 的存在性已确认（上面那串路径）；它是否会像全局 CLI 那样拒绝 `desktop` 档案，**尚未实测**。

**落地前要做的三条只读/可回退验证**：

1. 用官壳自带的 CLI 起一个 `web` 宿主：确认**不产生任何窗口**，且 `/api/wallpaper/v1/status` 返回 `bridge-ready`；
2. 用同一份 CLI 试 `--profile desktop`：确认是否同样被拒（决定"打开完整壳"那条路要不要另想办法）；
3. 会话互通：后台宿主里发一条，打开完整壳确认看得到同一条，反向再试一次。

三条通过之后再改代码。**输入岛左下角那个只读状态胶囊**正好承担这套新语义：`API` / `Web`（API 后端）、`Web` / `Desktop` / `TUI`（harness）。
