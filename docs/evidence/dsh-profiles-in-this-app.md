# 档案（Profile）在**本应用**里是怎么用的

记录时间：2026-09-30。本文只讲**我们这一侧**的流程（设置怎么存、启动怎么用、什么时候会自动改）；
DSH 自己的语义（档案按名字共享、会话按 `DSH_HOME` 归属、`desktop` 被壳独占）在
`dsh-profiles-ports-and-sessions.md` 里，两者互补。

---

## 一、一页结论

| 问题 | 答案 | 依据 |
| --- | --- | --- |
| 档案存在哪 | 设置里的**一个字符串** `dshLaunch.profile`，默认 `desktop` | `settings/store.ts:254`、`:467-470` |
| 谁用它 | 源码检出与已安装 CLI（都显式传 `--profile`） | `harness_launch.rs:589-605`、`:735` |
| 官壳用它吗 | **完全不**。壳靠 AUMID 激活，档案固定是它自己的 `desktop` | `launch_shell(aumid, alias, port, hide_window)` —— 签名里就没有 profile |
| TUI 用它吗 | **完全不**。TUI 给自己的档案命名（`dsh-tui`） | `harness_launch.rs:695-705` 的注释与命令形状 |
| 切换主体会不会换档案 | **不会**，除了"已安装的 CLI + desktop"这一种自动纠正 | `SettingsWindow.tsx:284-292`、`:950-960` |
| 切换档案会不会搬文件 | **不会**。它只是命令行参数，指到哪个目录就用哪个目录里的东西 | `installed_cli_command` 只拼参数 |
| 应用会去读 `~/.dsh/profiles/<名字>` 吗 | **不会**。整份 Rust 里没有读档案目录的代码 | 全仓检索无命中 |
| 档案不存在会怎样 | 应用不知道，DSH 自己报错（如 `profile "tui" does not exist`） | 实测见过这条错误文本 |
| 档案与桥的关系 | **桥是装在档案里的**（`file:` 依赖 + `node_modules` 副本）⇒ 换档案就换了一份桥，那份可能**没装**或**是旧的** | README「更新已安装的 Bridge」；本文件第六节 |

## 二、`web` 是被特判两次的那个档案

`web` 不是一个普通取值，代码里有两处硬绑定（各带理由）：

1. **`--no-open` 只在 `web` 上加**（`harness_launch.rs:735-745`）。理由是那面旗标属于 **web 应用自己**
   ——`dsh web` 默认"起服务并打开浏览器"，而壁纸认为"要不要开界面由我决定"（设置里选的是浏览器还是
   TUI，自启时更不该弹窗）。别的档案的 app 未必认这个参数，所以只对它加。
2. **网页交接只在 `web` 上做**（`harness_launch.rs:605`：`wants_handoff = profile.trim() == "web"`）。
   只有这条路上才会去捕获 CLI 的标准输出、解析它打印的 `http://127.0.0.1:<port>/?token=…`，从而
   知道该开哪个地址。

⇒ 换句话说：**把档案从 `web` 改成别的名字，等于同时关掉"不开浏览器"与"网页交接"两件事**。这不是
bug，但改动它的人必须知道这两处耦合。

## 三、三处自动纠正（都会当场说出来，不静默改设置）

`SettingsWindow.tsx` 的同一个 if-else 链上：

1. **主体不再受支持**（第三方客户端 2026-09-27 被移除）⇒ 落回官方桌面客户端并说明原因（`:280-283`）；
2. **已安装的 CLI + 档案还是 `desktop`** ⇒ 改成 `web` 并提示
   「已安装的 DSH CLI 用 web 这个档案（它自己那一个）；原来的 desktop 属于桌面客户端，会让它启动后
   立刻退出 —— 已改正。」（`:284-292`）。理由是实测：`--profile desktop` 启动它立刻退出，换 `web` 一切正常。
   切换主体时同样只在这个组合下替换（`:950-960`），而且**用户自己填过的档案不动**。
3. **显式端点是上一个主体的端口** ⇒ 清掉它（`:293-`），否则"用户 pin 优先"这条正确规则会按旧端口去开新界面。

留一处已知的粗糙：`desktop` 既是默认值、也是一个合法取值，所以"用户**特意**填了 `desktop` 给 CLI" 也会
被第 2 条改掉。判断依据是"值等于默认值"，而不是"用户有没有动过它"——设置里没有"动过"这个信息。

## 四、启动时的命令形状

| 主体 | 实际命令行 |
| --- | --- |
| 源码检出 | 它自己的启动链 + `--profile <档案>` + 启动参数（`harness_launch.rs` 的 managed 链） |
| 已安装 CLI | `dsh --profile <档案> [--no-open（仅 web）] <启动参数>` |
| 官壳 | `explorer.exe shell:AppsFolder\com.deepseek.dsh` —— **没有档案参数** |
| TUI | `cmd /c start "" <tui 启动器> <启动参数>` —— **没有档案参数** |

## 五、切换档案时到底发生了什么

**什么都没搬家**：档案只是启动器的一个参数，指向 `$DSH_HOME/profiles/<名字>` 那个目录。所以：

* 同一个档案跑两个端口 = 两个进程共用那一份磁盘状态（详见另一份证据文档）；
* 换档案 = 换了一整套插件清单、依赖树与提示词（`dsh.profile.bundles` 决定装什么）；
* 会话与工作区**不跟着换**——它们按 `DSH_HOME` 归属，跨档案可以恢复同一条会话。

## 六、档案与 Bridge 的安装是绑定的（用户最容易踩的地方）

桥是**装在某个档案里的**（profile 的 `package.json` 里一条 `file:` 依赖 + `node_modules` 里的副本）。
因此：

* 当前档案里没装桥 ⇒ 界面上是 `web-only`：*"检测到 DSH 服务，但壁纸 Bridge 未安装、未启动或不兼容。"*
* 当前档案里的桥是旧副本 ⇒ `bridge-incompatible`：*"…profile 内可能是过旧的副本，请更新 Bridge 后重试。"*
* **换一个档案就要重新确认那份桥**。应用自己不会装也不会更新（README 明确承诺"壁纸自身不会在后台执行
  包管理、下载代码或改写 DSH profile"），只有只读探测：它靠 `/api/wallpaper/v1/status` 判断，而不是去读
  档案目录。

## 七、设置里那行说明是错的（已修）

原文：**「这份源码使用的档案名；不同档案的会话互不相通。」**

* 后半句与实测相反：会话按 `DSH_HOME` 归属，**跨档案可以恢复同一条会话**，档案之间并不隔离会话；
* 前半句也不准确：它同时管着已安装的 CLI，而官壳与 TUI 根本不看它。

已改为如实描述（见本节之后的代码改动）：说明它管哪些主体、以及"档案决定装载哪些插件与提示词，
会话与工作区按 DSH 主目录共享"。

## 八、未验证

  with 'dsh plugin --profile tui add <package>'`，检出那条没测过）；
* 官壳的档案能否用 profile patch 改动（另一份文档里同样标为未验证）；
* `--no-open` 之外的 web 应用旗标（如 `--host`、`--trusted-host`）我们没有用到，未验证。
