# 桌面助手：跨日边界、项目记忆与人设简报（实施方案）

这份文档把三件事落成可施工的设计：**"助手日"的跨日边界**（用户提议：四点为界）、**桌面会话自己的项目记忆**、以及**用上下文注入把人设与规则讲清楚**。目标只有一个：用户对桌面的期待（"我让你做的事，你要记得；你是谁、能做什么，你要说清楚"）变成结构，而不是靠运气。

## 0. 非目标

- 不自动抓取全电脑内容进记忆（隐私）；只记**用户明确要求持久化**的东西。
- 不覆盖宿主（DSH）自己的人格/部署人设，只做**补充说明**。
- 不改 DSH 的归档语义；归档后的行为沿用今天已经落地的"换一条新会话"。

## 1. 现状（都是今天在真机上读到的）

### 1.1 跨日：用的是**系统本地时间**，没有"北京时间"这个概念

| 位置 | 事实 |
|---|---|
| `wallpaper/src/settings/store.ts` `localCalendarDay(now = new Date())` | 取 `getFullYear/getMonth/getDate` ⇒ **系统本地时区的日历日** |
| `bridge/src/index.ts` `localDailyWallpaperSessionId()` | 同样三段日期 ⇒ 会话名 `wallpaper-YYYY-MM-DD` |
| `wallpaper/src/App.tsx` `shouldStartNewConversationOnUnlock(policy, previousUnlockDay, now)` | `daily` 策略下：**本地零点后的第一次解锁**才换新会话 |
| 这台机器 | `Get-TimeZone` = `Singapore Standard Time`（UTC+8，与北京同一偏移），但代码里**没有任何时区换算**，也没有"北京"这个常量 |

⇒ 结论：**按系统时间**。所以它在 UTC+8 的机器上与北京时间一致，换台机器就不一定。而且两侧本来就**不完全对齐**：桥在**零点整**就换日会话 id，前端要等**零点后的第一次解锁** —— 差一个"解锁"事件，用户 00:30 重启壁纸就会拿到新一天的会话，而界面上那句"新的一天"还没发生。

### 1.2 人设注入的**唯一入口**已经在桥里

- `bridge/src/index.ts:288` `desktopEntryPrompt(cwd, workspaceTitle, permission)`
- `bridge/src/index.ts:302` `desktopAgentSetup(...)` → `setup: { text: desktopEntryPrompt(...) }`，创建/恢复会话时都在用（三处调用点）

今天它只说三件事：这是桌面入口（不是完整 Web UI）、工作目录是哪、权限预设是什么。**要讲的身份、能力边界、人格与记忆规则，都还没写。**

### 1.3 「人格」= **说话人格**，与立绘无关（用户 2026-09-27 明确）

用户说的"人格"指**说话人格**：语气、称呼、边界、要不要先问。**立绘/形态/气泡**是**外观**，与人格是两件事，不要混为一谈（本文档初稿把它们并在一张表里，是错的，已改）。

| 层 | 载体 | 用户怎么改 |
|---|---|---|
| **说话人格**（用户所指的"人格"） | ① 部署人设 + 1.2 那段简报；② 项目记忆里的称呼/语气条目 | **今天没有入口** —— 本方案补：设置里一项"说话人格"说明 + 简报模板 + 记忆条目 |
| 外观（立绘/形态/气泡/称呼标签） | 设置中心「形态」/「外观」、`bubbleOverrides`、`speakerLabels`、`BUILTIN_PERSONAS` | 设置中心 →「形态」/「外观」 |

简报里必须把这条**说给用户听**：改说话人格＝跟助手说（它写进记忆）；改外观＝去设置。两者不要互相暗示。

### 1.4 记忆：宿主已经有，而且这个 profile 已经装了

- 这个 profile 的 `dsh.profile.bundles` 里有 **`dsh-memento 0.4.2`**（跨会话记忆；写入要用户批准 —— 正好符合"不擅自替用户决定"）。
- DSH 自己的会话转写是**持久**的：`~/.dsh/sessions/<cwd 编码>/<sessionId>/session.v4.jsonl.zstd`，每条记录形如 `{ type, seq, time, data }`，其中 `session/title` 是标题、`time` 是时间戳（今天解出来的）。
- 桌面工作区 `%LOCALAPPDATA%\com.dsh.wallpaper\桌面会话` **卸载后保留**（今天验证过）。

## 2. 设计一：「助手日」—— 四点为准的跨日边界

### 2.1 规则

```
assistantDay(now) = localCalendarDay(now - boundaryHours 小时)
boundaryHours = 4（默认，可配）
```

- 一条**助手日**从本地 **04:00** 开始，到次日 03:59 结束。用户 00:30 还在做事，那条会话/那次重置仍算**前一天**。
- 会话名、解锁重置、岛上日期标签、② 的"同名取最近活动"，全部以 `assistantDay` 为准 —— **一个函数，两侧同值**。

### 2.2 落地方式（两处实现 + 一处自检）

1. 前端：设置里加 `dayBoundaryHour: number`（默认 4）；`localCalendarDay` 的调用点改走 `assistantDay(now, boundaryHour)`。
2. 桥：config 加 `dayBoundaryHour`（默认 4，写进 profile 的 `cordis.patch.yml`，用户可改），`localDailyWallpaperSessionId()` 改走同一个算法。
3. **自检**：壁纸启动时读一次桥的 `/status`（今天已经有 `capabilities` 这类自描述字段），把桥用的边界小时一起报回来；两边不一致就在桥日志与设置页各说一句（**不猜、不静默**）。

### 2.3 必须写清的边界情形

- **00:00–03:59 建的会话属于前一天**（名字与标签都是前一天的）。
- **四点整仍在进行的一轮不打断**：重置只发生在"下一次空转/下一次解锁"，与今天"解锁才换新会话"的策略一致 —— 用户正在说话时换会话是最坏体验。
- 用户改边界小时数**不追溯**已有会话名（改名会让归档/恢复对不上）。
- 归档后的 `-recovered` 替代名沿用同一套 `assistantDay`，否则归档恢复会把"前一天"的会话带回今天。

### 2.4 验收

- 纯函数测试：03:59→前一天、04:01→当天、跨月/跨年、`boundaryHour = 0` 时退回旧行为。
- 真机一次：把机器时间挪到 03:59 与 04:01 各发一句，看会话 id 与岛上标签（时间只在测试时挪，事后立刻改回）。

## 3. 设计二：桌面会话的「项目记忆」

### 3.1 两层，各司其职

| 层 | 位置 | 谁写 | 为什么 |
|---|---|---|---|
| **AI 侧记忆** | 宿主已有的 `dsh-memento`（跨会话，写入需批准） | 助手；用户批准 | 让"以后都这样"活过会话 |
| **人可读记忆** | `桌面会话/项目记忆.md`（数据目录里的桌面工作区，卸载保留） | 助手维护，用户随时自己改 | 用户能看见、能纠正；不依赖任何插件是否装着 |

### 3.2 规则（写进 1.2 的简报里）

- 用户说"记下来 / 以后都这样 / 别再问" ⇒ **写进记忆**；写完回一句"记下了：…"（可核对）。
- 每次会话**开始先读** `项目记忆.md`；与用户此刻的说法冲突时，**以用户此刻为准**，并把旧条目标注为"已被 X 取代"（**不静默删除**）。
- 记忆只放**要求与偏好**（做什么、怎么做、不要做什么、称呼与语气），不放敏感内容、不放一次性任务。
- 记忆里关于称呼/语气的条目要能影响简报里的 `{{personaName}}` 之类变量。

## 4. 设计三：人设简报（briefing）与上下文注入

### 4.1 单一入口

把 `desktopEntryPrompt` 升级成**桌面助手简报**，仍然由 `desktopAgentSetup` 在创建/恢复会话时注入（唯一入口，避免"两处话不一致"）。

模板变量：`{{cwd}}`、`{{workspaceTitle}}`、`{{permission}}`、`{{assistantDay}}`、`{{personaName}}`、`{{memoryPath}}`。

### 4.2 内容分四段（措辞以"只说真话"为准）

1. **身份与场景**：你是**桌面壁纸助手**，用户通过桌面上的输入岛跟你说话，看不到完整的 Harness 界面；因此要用一句话把"发生了什么、接下来做什么"说清楚，不要假设他能看见工具面板。
2. **能力与边界**（今天验证过的事实）：
   - **读**：可以搜索并读取**整台电脑**上的文件来解答疑惑（读是全局放行的）。
   - **写**：只允许在桌面会话目录内写（沙箱是 `workspace-write` = 全局可读、只在工作区与私有临时目录内可写）。越界写会被**沙箱直接拒绝**，这时候的正确动作是**告诉用户**"这块需要把目录放进桌面会话，或者你把权限提上去"，而不是反复重试。
   - 危险操作要**先问**；与用户当前要求无关的改动不要顺手做。
3. **人格与外观怎么改**：话术给用户 —— **说话人格**（语气、称呼、要不要先问）**跟助手说**，它写进项目记忆；**外观**（立绘/形态/气泡）去**「设置中心 → 形态 / 外观」**。两者要分开说，别让用户猜。
4. **记忆规则**：按第 3 节的规则办；`项目记忆.md` 的路径直接写在简报里，让用户也能自己打开。

### 4.3 与宿主的关系

这是**部署人设的补充说明**，不覆盖宿主的人格：语气可以延续宿主，**边界与记忆规则以这里为准**（它们是这个桌面的产品事实）。

## 5. 分期（每期都可独立验收）

- **P0（小）**：`assistantDay` 纯函数 + 两侧同值（默认 4 点）+ 简报文本 v1 + `项目记忆.md` 约定。**今天就能做**。
- **P1**：设置项（边界小时、记忆路径）、启动自检、岛上日期标签跟随、`/status` 回报边界小时。
- **P2**：② 命名规则（改用 workspace API 的标题/最近活动，不再解析 JSONL）、记忆条目的人工审阅界面（可选）。

## 6. 决策点（需要用户定）

- **D1**：默认边界 **04:00** 对吗？重置时机取"**下一次解锁/空转**"（推荐）还是"四点整立刻换"？
- **D2**：允许把 `dayBoundaryHour` 写进 profile 的桥配置（用户可改）吗？还是让壁纸把设置推给桥（需要桥开一个设置入口）？
- **D3**：记忆坚持**两层**（memento + 人可读文件）还是只留一层？
- **D4**：简报里怎么写能力边界？建议就按 4.2 的措辞（**可读全盘、只在桌面会话内可写、越界就明说**）—— 这是今天在真机上验证过的事实。

## 7. 验收（可执行）

1. 纯函数：`assistantDay` 的边界、跨月跨年、`boundaryHour=0` 回归旧行为。
2. 真机：03:59 / 04:01 各发一句 → 会话 id 与岛上标签；
3. 简报生效：开一条新会话，第一轮问"你是谁、能做什么、人格怎么改、记忆在哪" → 回答必须与 4.2 一致，并且**不承诺做不到的事**（例如"我能改任何系统设置"）；
4. 记忆生效：说一句"以后都先问我再改文件" → 被记下；新开会话 → 仍然生效；用户改口 → 旧条目被标注替代而不是消失。

## 8. 增设：扫描 DSH 档案 + 把桥装进去（用户 2026-09-27 提议）

**结论：同意，而且它治的正是今天暴露出来的两个真问题。**

### 8.1 为什么值得做（今天的证据）

1. **"装进 profile"这件事现在完全没有反馈**：桥是以**一份拷贝**的形式住在 profile 里的（`<profile>\node_modules\dsh-wallpaper-bridge\lib\**`）。今天为了让新代码生效，我连踩三坑：`pnpm install --force` 说 "Already up to date" 什么都不做；`pnpm update` 的参数在这个 pnpm 版本不接受；把目录删掉重装 pnpm 也不重建（只好手工复制 + 重启 DSH）。**"扫描 → 用户选 → 我们装 → 我们验证"** 把这一串不确定性收进产品。
2. **"下次重启后生效 / 打开 DSH 后生效"必须由我们用事实回答**，而不是让用户猜。事实来源是探测该档案端点的 `/api/wallpaper/v1/status`：

| 探测结果 | 含义 | 该说的话 |
|---|---|---|
| 应答且桥自报 `state: bridge-ready` | 已生效 | "已连接" |
| 应答但**不是**桥（404 等） | DSH 在线、桥未加载 | **"bridge 将在下次重启后生效"** |
| 不应答（没有进程在听） | DSH 不在线 | **"bridge 将在打开 DeepSeek Harness 后生效"** |

（今天这两种应答我都亲眼见到过：19387 上 404 与 200 各命中一次，所以这条判断是可实现的 ✓。）

### 8.2 设计要点

- **扫描**：`%USERPROFILE%\.dsh\profiles\*`（每个含 `package.json` 的目录 = 一个档案；它的 `dsh.profile.bundles` 就是已启用插件清单）；与"已装的 shell（AUMID）"和"用户当前选中的档案"三者的关系要在界面上说清。
- **选择即安装**：写该档案的依赖（`file:` 指向我们的 bridge）+ 把 `dsh-wallpaper-bridge` 加进 `dsh.profile.bundles`，然后跑一次安装并**校验结果**（比对 `lib` 哈希，或读 `/status` 的 `capabilities`）。**"装完要能证明它生效"是这条功能的灵魂** —— 今天正是"看着装了、其实没生效"。
- **绝不静默改别人的档案**：只在用户明确选择时写，改前备份被改的文件（`package.json` / `cordis.patch.yml`），并把"改了什么、怎么撤回"写给用户。今天用户已经为 profile 层面的事付过一次代价。
- **多档案**：可以有多个候选项，但同一时刻只有一个"壁纸在用的档案"（沿用今天的 `dshLaunch` 主体选择）。
- **用户可以不配置**：没有档案 ⇒ 岛上滑槽**永远在左（关）且禁用**，禁用原因写明"未配置 DSH：设置 → 选择一个要使用的 DSH 档案"。这与今天 `canSelectBackend` 的语义一致（没就绪就不能切到 harness），差别是**它要变成一个干脆、不闪的状态**（今天滑槽会在黄/绿之间呼吸，没配置时不该给人"也许能点"的错觉）。
- **在线状态会变**：DSH 后来起来了怎么办？沿用今天的监控（`monitorHarnessEndpoint` 周期探测）—— 一旦端点应答且桥自报 ready，滑槽**自己变得可用**，用户不必重启壁纸。这条必须写进提示语，否则"下次重启后生效"听起来像"你必须重启壁纸"。

### 8.3 分期

独立于 P0（P0 无依赖、今天可做）。建议排在 **P1**，与"边界小时设置项 + 启动自检"同批 —— 它们都落在设置页上，一起做省一轮往返。
