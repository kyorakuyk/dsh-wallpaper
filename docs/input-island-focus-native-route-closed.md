# 输入岛键盘修复：原生路线终止证据与后续两案

对应施工文档：`input-island-keyboard-focus-repair-plan.md` §3.A、§3.B。
记录时间：2026-09-25 08:11（进程时钟）。基线提交 `e7c902f`。

## 1. 原生路线已无入口（实测，非推断）

先确认了测量本身的可靠性，避免重犯此前「工具盲区当成事实」的错误：

```
运行中进程启动时间 : 09-25 08:10:04
exe 编译时间       : 09-25 08:10:01      -> 进程晚于编译，探针确实在运行
日志最后写入       : 09-25 08:11:44      -> 该次真实点击落在探针生效之后
```

一次真实左键单击输入岛，子类过程记录到的仍只有：

```
focus trace [WM_ACTIVATE/WM_SETFOCUS]:
  foreground=Progman  focus=Tauri Window
```

而以下三条**一次都没有出现**：

| 事件 | 到达情况 |
| --- | --- |
| `WM_MOUSEACTIVATE` | 从未 |
| `WM_LBUTTONDOWN` / `WM_NCLBUTTONDOWN` | 从未 |
| `WM_NCHITTEST` + 左键按下（新增探针） | 从未（探针确认在运行） |

结论：**鼠标消息与命中测试均由另一进程的 WebView2 子窗口处理**，我们的子类过程
既收不到点击，也看不到命中测试。因此**不存在"在那次点击的时序内请求激活"的原生入口**。

同时此前的读回已经证明键盘通道拿不到：

```
SetFocus 返回成功，但 foreground_is_wallpaper=false
```

对 `Progman` 的子窗口 `SetFocus` 只能设置本线程焦点，不能使其成为全局前台。

**这满足文档 §3.B 的停止条件：`Progman`/`WorkerW` 子窗口无法稳定获得全局键盘通道。**
故停止该路线，按文档要求提交受限方案，不自作主张继续在原结构上叠加。

## 2. 两案对比

### 方案甲：前端 `pointerdown` + 原生命令核验（文档 §3.A 已预留）

前端在输入岛 `pointerdown` 时请求一个原生命令；原生侧在**执行任何激活之前**核验：

1. 物理左键确实按下（`GetAsyncKeyState(VK_LBUTTON)`）；
2. 光标位置落在**已声明的交互热区**内（复用 `interaction_regions()`，不新增几何）；
3. 光标下的 HWND 父链**属于壁纸**（防止任意 IPC 调用被当成用户点击）。

核验通过后执行前台交接，并读回 `GetForegroundWindow`、`GetGUIThreadInfo(0).hwndFocus`
以及页面 `document.activeElement`。

**关键优势**：由真实输入事件触发的进程**解除前台锁**，此时 `SetForegroundWindow`
是被允许的。这正好补上了"子窗口无法仅靠 `SetFocus` 取得前台"的缺口。

风险：新增 IPC 入口，必须把能力限定在 `background` 表面（Lite 与远程网页窗口不得获得），
并在 `build.rs`、`capabilities/background.json` 同步权限。核验若不成立必须拒绝而非静默执行。

### 方案乙：受限顶层交互层

新增一个**仅覆盖输入岛热区**的可激活顶层窗口，承载键盘输入。

需要的窗口层级、热区与多屏风险：

- **窗口层级**：顶层 `WS_POPUP`（可激活），置于壁纸之上、仅覆盖输入岛矩形；
  与现有 `interaction_regions()` 几何一一对应，随 DPI/分辨率变化同步。
- **热区**：不扩大整张壁纸的可点击面积；热区外必须完全不拦截输入，桌面图标、右键菜单、
  任务栏、设置窗口、全屏应用的行为不得改变。
- **多屏风险**：主副屏、负坐标、不同 DPI 下热区矩形需逐屏换算；跨屏切换与分辨率变化时
  需重新定位，否则会出现"窗口悬在错误屏幕"或"挡住别的应用"。
- **全屏应用**：必须确保全屏时该窗口不抢前台。

风险显著高于甲：引入了新的顶层窗口生命周期、Z 序与多屏几何，且与"壁纸不抢前台"的
承载性设计直接冲突。

## 3. 建议

**先做方案甲**。理由：

1. 文档 §3.A 已经预留该路径及其核验要求，属于许可范围；
2. 真实输入事件会解除前台锁，使前台交接**有资格**成功，而这正是当前失败的原因；
3. 不改动窗口层级，不新增顶层窗口，多屏与全屏风险不增加；
4. 核验条件明确且可测（左键、热区、HWND 归属），失败即拒绝。

若方案甲在真机上仍无法取得全局键盘通道（读回仍为 `foreground_is_wallpaper=false`），
则说明问题不在触发方式而在窗口层级本身，届时再实施方案乙。

## 6. 补充取证：交接读回判定「Progman 子窗口路线」不可用

时间：2026-09-25 08:29（进程 46804）。一次真实点击的交接读回：

```
交接结果：附接=false SetForegroundWindow=true SetFocus=true
  | 读回 前台=Progman(pid=30940) 焦点=Chrome_WidgetWin_1(pid=36688) 壁纸pid=46804
```

两个 API 均返回成功，但读回不是可用形态。与实测到的「能用」形态对比：

| 状态 | 前台 | 全局焦点 | 焦点根 == 前台根 |
| --- | --- | --- | --- |
| 能用（同一台机器实测） | `Tauri Window`（本进程） | `Chrome_WidgetWin_1` | **True** |
| 交接后（不能输入） | `Progman`（Explorer） | `Chrome_WidgetWin_1` | **False** |

判据因此确定为：**焦点链的根必须就是当前前台窗口**。宿主挂到 `Progman` 之后，
`GetAncestor(host, GA_ROOT)` 返回 `Progman`，把前台交给它只会得到「前台是 Progman、
焦点根却是我们的 Tauri Window」这种不一致状态，键盘仍然进不来。

这也解释了用户报告的三条现象：

- 最小化窗口**第一次**偶然可用：那一刻宿主处于顶层形态；
- **第二次以后完全不行**：已回到 Progman 子窗口形态；
- **重启壁纸也不行**：重启后会重新挂载到 Progman，直接进入不可用形态。

结论：**现有结构（Progman 子窗口）无法取得一致的全局键盘通道**，满足 §3.B 的停止条件。
本路线终止，改为实施 §2 的方案乙（受限顶层交互层），并以上文判据作为验收读回。
交接实现保留但不再视为可用；其读回日志正是得出上述结论的依据。

用户提出的「似乎是绑定的窗口」与本节结论一致：可用性取决于宿主窗口的层级形态，
而非按键内容或输入组件本身。
