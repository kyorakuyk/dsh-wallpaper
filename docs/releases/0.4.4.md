# DSH Wallpaper 0.4.4（完整版 · Windows 11）

这一版只做一件事：**让更新回到"一步"**。

## 问题（真机实测报回来的）

点「点击安装」之后，用户看到的是**两步**：

> 会先弹一个 **uninstaller**，然后接 **installer**

卸载器先跑、再装新版，这是 Tauri NSIS 的正常升级顺序（先卸旧、再装新），**而且它本来就该是静默的**。它没静默，原因是：**安装时应用自己还在运行**——安装器替换不了被占用的 `dsh-wallpaper.exe`，于是把本该静默的卸载器**弹成了可见窗口**让你处理。

（旁证：开发过程中每次在本机装新构建，都必须先停掉正在运行的进程，否则安装会失败——同一个原因。）

## 改法

点「点击安装」时：

1. **先安排一个"守候者"**：一个分离的、比应用活得久的助手，它的唯一职责是**等待本应用进程结束，然后启动安装器**；
2. **应用随即优雅退出**（与托盘「退出」同一条路：恢复桌面图标、清理原生状态、标记干净退出）；
3. 安装器在"没有人占用 exe"的机器上跑 ⇒ 卸旧那一步回到**静默** ⇒ 你看到的从"卸载器 + 安装向导"变成**一个安装向导**；
4. 装完由 NSIS 的完成页**启动新版**。

**回落不静默**：如果守候者起不来（极端受限环境），**不退出**，当场打开安装包，并在界面上如实告诉你"没能安排退出后再安装，已直接打开安装包"——而不是退出之后什么都不发生。

## 施工中实测出来的两个坑（都已写进代码注释与测试）

| 坑 | 现象 | 结论 |
| --- | --- | --- |
| `-WindowStyle Hidden` 搭配 `-EncodedCommand` | PowerShell **14 毫秒就退出、脚本一行都没跑** | 不留黑框必须靠 `CREATE_NO_WINDOW`（进程级），不能用那个参数 |
| `Wait-Process -Id … -ErrorAction SilentlyContinue` | **目标进程还活着也立刻返回**（13 毫秒） | 改成对进程对象 `$p.WaitForExit()`；实测等满 5 秒的目标 |

另有一条 `#[ignore]` 的**真进程测试**：拿 `notepad` 当目标，验证"守候者确实等到进程结束才启动它"。

## 关于验证顺序（重要）

**这一版本身还不是"一步更新"的证明**——因为**正在运行的那个版本**（0.4.2 / 0.4.3）里没有这次改动，它点安装时仍会走旧流程（先弹卸载器）。

要看到"一步"，顺序是：

1. 先用现在这条链升到 **0.4.4**（可能仍会看到卸载器窗口——那是旧行为）；
2. **下一次**再从 0.4.4 更新（例如将来的 0.4.5），才能看到"应用自己关掉 → 一个安装向导 → 自动起新版"。

## 更正（0.4.6 施工时发现，原文不改、在此说明）

本文把"可见的卸载器窗口"归因为"应用仍在运行、安装器替换不了 exe"。**那个归因是错的**。0.4.6 施工时读安装脚本并做了对照实测，真正的根因是：**Tauri 的 NSIS 模板调用旧版卸载器时从来不传 `/S`**（测法：给一个探针卸载器分别传 `_?=<目录>` 与 `/S _?=<目录>`，前者在卸载器内 `${Silent}=0` ⇒ 带界面，后者为 1）。

所以："应用先自己退出"（0.4.4）解决的是**另一件事**（exe 被占用时卸载/覆盖会失败），它仍然必要；而"两步"这个现象，要由 0.4.6 的自定义模板给卸载器加 `/S` 才消失。
