# DSH Wallpaper 0.4.9（完整版 · Windows 11）

修一个"**滑槽拨不过去**"的问题，并带上启动时间的测量点。

## 修了什么：滑槽被自动拨回去

**现象**：输入岛右上角那个"滑槽"（网页入口 / API ⇄ Harness 的后端开关）拨到左侧后**立刻自己弹回**，看起来像"点击无效"。

**原因**（有证据，不是推断）：前端有一条自动规则，只看"设置里开着自动切换 + 桥已就绪 + 当前不在 Harness"，**不看这个开关是谁拨的**。于是你每次手动拨到左侧，它就把你拨回来。

证据在本机浏览器的本地存储时间线里：`dsh-wallpaper:conversations:v1` 的 `updatedAt` 在 09:50 到 09:54 之间出现**七轮"API 与 Harness 成对、相差不到一秒"**——说明点击**确实生效过**（对应后端的聊天适配器真的建立过），只是立刻被拨回去。

**为什么现在才出现**（这点值得记下）：以前那个桥端口上**没有桥**，这条自动规则从不生效；今天随壁纸启动的 CLI 把桥跑起来了，**潜在缺陷第一次真的动手**。所以这不是 0.4.8 引入的，是**桥梁上线暴露的旧缺陷**。

**改法**：把两条自动规则合成一个判据，并记住"用户把开关停在左侧"这个状态——

- **没碰过开关的启动**：桥就绪后仍然自动切到 Harness（设置的作用范围不变）；
- **手动拨过之后**：自动规则不再把它搬走。

就绪判据、指示灯、点击路由、原生命令、托盘菜单都没有改动。前端测试 540 → 541（新增一条回归：就绪且用户没碰过仍自动切；用户手动拨过后两条规则都不许搬走）。

## 顺带带上：启动时间的测量点

这一版包含启动链上的计时日志（进程入口 → 崩溃自证就绪 → 单实例确认 → Builder 装配 → setup → 原生首帧 → 宿主挂上 → 更新清理 / Harness 监视 / 悬浮球），**只加计时，没有改任何启动顺序**。配套脚本 `scripts/measure-startup-gap.ps1` 可以算出"**登录 → 本进程启动**"这段——它看不见的那一段恰恰是决定"要不要改用登录触发器计划任务"的依据。

## 已知未修（写在这里，不等你自己撞上）

**"停在 Harness 且桥未就绪"时，滑槽拨不回左侧**，要等约 45 秒握手失败后由壁纸自己复位。那段代码上方的注释原本就写着"必须永远能切回去"，**注释与代码在这里不一致**。本次没有证据表明它被触发，所以没有改动——但它是个真实的坑，应当单独修。

## 怎么验

1. 设置 → 连接 → 保持「DSH 就绪时自动切换」**开启**（这是暴露缺陷的条件）；
2. 等指示变绿，在输入岛上把滑槽拨到左侧：**应当停在左侧不再弹回**；再拨一下能切回 Harness；
3. **反向确认**（别把设置功能改坏）：重启壁纸、**不碰**滑槽，桥就绪后应自动切到 Harness；
4. **一键旁证**：操作前后看
   `%LOCALAPPDATA%\com.dsh.wallpaper\EBWebView\Default\Local Storage\leveldb\` 里 `dsh-wallpaper:conversations:v1` 的 `updatedAt`——
   修好前是"两个后端成对、相差不到一秒"，修好后只应出现**一个**后端的时间戳。
