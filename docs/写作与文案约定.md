# 写作与文案约定

这份文件记的是**用户明确提出过、并且被违反过**的要求。写在这里而不是留在某次会话的记忆里：会话会结束，仓库不会；下一个人（或下一次我）读到这里就够了。

## 一、不要用 ✓ / ✗ 标记

用户提过三次。前两次我答应后仍然复发，所以这一条排在第一位。

- **不要**在句尾、要点后、表格单元格里放 ✓ / ✗ 当作"已查证 / 未成立"的装饰。
- **不要**用它们标注用户的说法（那会把对话变成批改作业）。
- 确实需要裁决时（比如"是 / 否"两栏），**用文字**：`是`／`不是`，或者干脆写成一句话。
- 同理克制其它符号堆砌（彩色圆点、箭头串）。

## 二、表格只在确实更清楚时用

同一件事能用一句话说完，就不要摊成表格。表格是给"多维对照"用的，不是排版习惯。

## 三、界面文案说"这是干什么"，不说"这是什么"

- 描述里写**用户能拿它做什么**，不要写实现结构（"这不是 X 而是 Y"那种架构腔）。
- **不要为显而易见的事加一句解释**。用户的原话：提醒一个人人都能意识到的事情，会让那个人觉得"这难道不一样吗？"，进而想偏。
- 一句话能说完的，不要写成两句。

## 四、提交信息

- 英文，叙述式，讲"为什么"和"证据"，不复述 diff。
- 测试红着的时候不提交；闸门（typecheck / 测试 / cargo）绿了再提交。
- 只 stage 自己的文件：别的工作流的 WIP（README、packaging、scripts、gen/schemas 等）不进自己的提交。
