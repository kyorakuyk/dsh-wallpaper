# Harness 执行主体与「拉起 UI」：设计与已冻结决定

状态：**设计已定，未实施**。基线为 `codex/startup-render-handoff` 的 `a0d5aa0`（2026-09-26）。本文汇总 2026-09-26 讨论中钉死的决定、实测事实与已排除的假设，不含实现代码。

相关：登录自启项本身的稳定性问题见 [`../plans/autostart-recovery-plan.md`](../plans/autostart-recovery-plan.md)；"更新后自启失效"的修复见同目录 `../plans/dsh-harness-connection-autostart-compatibility-plan.md`。

---

## 1. 要解决的问题

壁纸今天只支持**一种** harness 形态：源码检出。设置里是"根目录 + profile + 启动命令"，而官壳与桌面这两个 Electron 壳**完全不在模型里**——壁纸既不知道它们存在，也无法拉起它们。

需要引入一个**内部垫片**：把"实际执行的是哪个 harness"这件事吃掉，使不同的执行主体对上层表现为**同一件事的几个可选项**。

术语（本文统一使用）：

| 词 | 含义 |
| --- | --- |
| **执行主体（服务）** | 真正提供 harness/bridge 的那个东西（检出本体，或某个壳自带的检出） |
| **窗口（UI）** | 用户看到的界面（浏览器 / 自带 GUI / 第三方 GUI/TUI） |
| **垫片** | 壁纸**内部**的一个模块，负责"起"和"找"，**不对外暴露** |

## 2. 实测事实（2026-09-26，本机）

### 2.1 三者的实际形态

| | 检出 | 官壳 | 桌面 |
| --- | --- | --- | --- |
| 存在形态 | **源码树，没有安装** | **Electron 应用**（NSIS 安装，非 MSIX） | **Electron 应用** |
| 主程序 | 无（靠 `node`/`pnpm`） | `D:\Family\dsh-official\DeepSeek Harness.exe`（244 MB） | `D:\Family\DSH desktop\DSH Desktop.exe`（225 MB） |
| 启动方式 | `node apps/cli/lib/bin.js --profile X`<br>或 `pnpm dsh --profile X`（cwd = 检出根） | 直接开 exe<br>或 `shell:AppsFolder\com.deepseek.dsh` | 直接开 exe<br>或 `shell:AppsFolder\ai.deepseek.dsh.desktop` |
| 身份指纹 | 目录含 `package.json` + `apps/cli`（可选 `apps/cli/lib/bin.js`） | AUMID `com.deepseek.dsh` + 安装目录 | AUMID `ai.deepseek.dsh.desktop` + 安装目录 |
| 默认端口 | 3080 | 19387 | 43120 |
| 更新方式 | `git pull`（可能需重建） | 重装包 | 重装包 |
| 需要参数 | 需要（`--profile`） | 未知（自有参数） | 未知 |

共同点（这是"可以收束"的基础）：都跑在本机回环、最终都提供 harness/bridge、都读同一个数据根 `~\.dsh`（含 `profiles\desktop`、`desktop.backup-*`）。

### 2.2 官壳的 asar 证据（112 MB 包内检索）

```js
// 单实例：第二次启动不会开出重复实例
if (!application.requestSingleInstanceLock()) { application.quit(); return false; }
application.on("second-instance", focusOwner);          // 再拉一次 → 把窗口带到前台

// 托盘：点击托盘 = 把主窗口弄到前台
tray.on("click", () => { options.open(); });            // open = focusPrimaryWindow()
tray = new DesktopTray({ iconPath: join(process.resourcesPath, "tray.ico"), … });

// 关窗即退出（非 darwin）
app.on("window-all-closed", () => { if (process.platform !== "darwin") app.quit(); });
```

**实测修正**：上面最后一段推论出"点 X 会退出"，但**用户实测点 X 是回到后台**——说明该壳拦截了 close 事件改为隐藏（这与托盘 + `focusPrimaryWindow` 的设计一致）。**实测优先于代码推断**；隐藏窗口不等于关闭窗口，所以隐藏后主进程与 19387 的 bridge 继续存活。

### 2.3 桌面

其 `app.asar` 仅 4.9 MB，**未检索到**单实例锁、托盘、隐藏启动相关的任何痕迹。因此对它**不能**使用"再拉一次程序"作为恢复手段（会开出第二个窗口），也不强求与官壳同等的隐藏能力。

### 2.4 壁纸侧已有的可复用能力

- `spawn_managed_dsh`：统一的启动路径，手工按钮（`launch_dsh`）与自动启动（`managed_dsh_autostart`）**共用同一实现**；
- 信任模型：`AUTO_START_LAUNCHER_ALLOWLIST`（`node`/`pnpm`）+ `command-not-confirmed` 确认；
- `scan_dsh_paths`（含 deep scan）：已有的静态扫描能力；
- `dsh_port_is_occupied()`：外部 DSH 占用 3080 时**不接管、不停止**；
- 窗口操作全套原生能力（`EnumWindows` / `ShowWindow` / `SetForegroundWindow` / `GetWindowThreadProcessId`）。

## 3. 两类模型（核心）

| 类别 | 用户看到的选项 | 执行主体 | 窗口 | 绑定关系 |
| --- | --- | --- | --- | --- |
| **自带检出** | 官壳 / 桌面 | **它自带的**检出 | 它自己 | 选了就同时定了主体与窗口，**不可拆** |
| **非自带检出** | 浏览器 / 第三方 GUI | **系统检出**（被指定的那一个） | 所选的那个 | 主体**固定**为系统检出，窗口**可换** |

用户流程：**先选执行主体**（官壳 / 桌面 / 系统检出）→ 若选"系统检出"，**再选窗口**（浏览器 / 第三方 GUI）。

要点：主体**不是自由组合出来的**，而是由类别决定的；设计只需围绕这两类。

---

## 4. 已冻结的决定

1. **垫片是壁纸内部模块**，不对外暴露、不新增独立进程。
2. **"起"和"找"都放在垫片里**，但二者机制不同（见 §5）。
3. **检测到多份系统检出**时，向用户提示："检测到您电脑上安装了多个 deepseek harness 源码树，请选择默认主体"。
4. **"系统检出"必须是一个被指定的靶点**，不得硬编码路径（否则重犯"写死路径、更新即失效"）。
5. **端口不写死为契约**：3080 / 19387 / 43120 只是各自的默认值，"找"必须能扫任意回环端口。
6. **保留既有原则**：多个实例可同时存在，切换只改"壁纸连谁、拉谁"，绝不接管或停止他人已在运行的实例。
7. **`profile` 设置项只属于"系统检出"这一路**；选了官壳/桌面时不显示（它们用自己的数据）。
8. **浏览器选择已冻结**：只提供"默认浏览器"，不提供浏览器选择器，也不改系统默认浏览器。
9. **TUI 已冻结**：本轮不做（若将来做，需同时解决"用哪个终端"，机制与"选浏览器"同形）。
10. **桌面（第三方）不强求兼容性**：开机自启时**直接拉起它自己的窗口**，不隐藏；避免为此增生 bug。
11. **第三方 UI/壳的"允许拉起"复用现有 `command-not-confirmed` 确认模型**。

## 5. 行为定义

### 5.1 「开机自启 DSH」= 起**执行主体**

- 系统检出：`dsh web` **本身没有窗口**（手工起时只打印一行 `dsh web: http://127.0.0.1:3080`）→ "只供能、不弹窗"**天然满足**；
- 自带检出的壳（官壳）：**先起服务、窗口隐藏**，等用户需要时再显示；
- 桌面：按 §4.10，直接带窗口拉起。

### 5.2 「拉起 UI」= 幂等地"让窗口到前台"（该功能目前留空）

必须覆盖三种状态：**主体没起 / 起了但窗口隐藏 / 窗口在后台**。顺序恒为：

> 先确认主体在跑（探针应答）→ 再让窗口到前台；主体不在则按 5.1 重起一次（这次不隐藏）。

### 5.3 与"web/harness 切换滑槽"的关系

**点滑槽与开机静默启动 harness 做的是同一件事**，唯一区别：点滑槽会**额外切换到 harness 模式**，开机自启**不切模式**。因此二者**复用代码极多**，实现时应共用同一条启动链，只把"是否切换模式"作为参数。

## 6. 边界情况与两条硬约束

1. **显示窗口以"我们自己操作那个 HWND"为主**（`ShowWindow(SW_SHOW)` + `SetForegroundWindow`）。原因：从外部用 Win32 隐藏窗口后，那个壳内部可能仍认为窗口"可见"，它自己的 `show()` 未必能把窗口找回来（**未验证，故不依赖**）。"再拉一次程序"只作为**单实例壳**（官壳）的补充手段；**对桌面禁止使用**（无单实例锁，会开第二个窗口）。
2. **若用户用 X 关掉了窗口**：官壳实测是隐藏（主体仍在）；但若某个壳真的整体退出，主体随之消失 → 「拉起 UI」必须能识别"主体不在"并**重拉整条链**，而不是傻等一个不会出现的窗口。
3. **窗口拉起失败必须可见**：第三方 GUI 同样会"起来就死"，须复用 `managed-dsh.log` 那套 stdout/stderr + 退出码捕获，否则又是一次"没有日志可查"。

## 7. 本轮已排除的假设（避免重复排查）

针对"壁纸拉起 DSH 后立即退出"这一现象，以下假设已逐条实测排除：

| 假设 | 验证方式 | 结论 |
| --- | --- | --- |
| 检出本身坏了 | 手工跑 `node apps/cli/lib/bin.js --profile desktop` 与 `pnpm dsh --profile desktop` | **都成功**，3080 正常监听 |
| stdin 被关闭/EOF 导致退出 | 子进程 stdin 喂立即 EOF | 不受影响 |
| GUI 父进程的 NULL 标准句柄 | 用任务计划程序起（默认无任何标准句柄） | **正常** |
| 硬崩溃 | WER 报告 / 应用事件日志 | **无记录** → 是干净退出 |
| 壁纸主动杀掉子进程 | 全仓库检索 kill 点 | 只有"停止"按钮与应用退出清理，运行期均不触发 |
| 端口被外部占用 | 该情况会走 `port-occupied-external` 分支 | 与所见提示不符，排除 |
| 检出根目录里的悬空硬链接 `_tmp_43592_*` | 检查其类型与目标 | 2026-09-12 的遗留物，与本次无关 |

**仍未确定的根因**：壁纸拉起的子进程为何在数秒内退出。原因是**DSH 的 stderr 被隐藏 console 吞掉**（见 §8），当前无法取得它自己的报错。

## 10. 附：与"自启项稳定性"的同一性

本设计与我方对登录自启项的修复属**同一个模式**：调用方只认一个**不变的入口**，由入口去解析当前真正的目标（Velopack 的执行桩、Squirrel 的 `Update.exe`、MSIX 的 `shell:AppsFolder\<AUMID>`，以及本项目自启项最终采用的 AppsFolder 别名）。此处只不过把该模式从"自启项"推广到"**执行主体的启动与寻址**"。

推论：**"发现"可以通用（协议指纹），"启动"不可能通用（进程形态各异）**——因此"扫描 + 手动添加"两种入口必须并存。
