# 代码导读（中文）

写给"想读懂这套代码"的人。目标不是逐句翻译注释，而是讲清**结构**、**数据怎么流动**、以及**为什么有些地方必须那么写**。

阅读建议：先看第 1、2 节建立地图，再按第 6 节挑一条路线深入。注释仍以英文为主（保持与其它 DSH 代码一致），但每个模块的"为什么"本文都给了中文说明。

---

## 1. 这是什么：三个部分 + 一条链路

```
                    ┌──────────────────────────────┐
   用户点桌面图标 →  │  wallpaper（Tauri 应用）      │
                    │  前端 src/  ←→  原生 src-tauri/│
                    └───────────┬──────────────────┘
                                │ 只走 127.0.0.1 的 HTTP
                                ▼
                    ┌──────────────────────────────┐
                    │  bridge（DSH 插件）           │
                    │  /api/wallpaper/v1/*          │
                    └───────────┬──────────────────┘
                                │ DSH 自己的 API / 会话
                                ▼
                    ┌──────────────────────────────┐
                    │  DSH 宿主（客户端 / CLI / TUI）│
                    └──────────────────────────────┘
```

- **`bridge/`**：一个 DSH **插件**（包名 `dsh-wallpaper-bridge`）。它被装进某个 DSH *档案*（profile）里，在宿主的 web 服务上挂出 `/api/wallpaper/v1/*`，把"壁纸要问 DSH 的事"翻译成 DSH 自己的 API 调用。**壁纸之所以能对话，全靠它。**
- **`wallpaper/`**：桌面应用。`wallpaper/src/` 是渲染层（React/TypeScript），`wallpaper/src-tauri/` 是原生层（Rust，管窗口、扫描、启动、截图、锁屏等）。
- **`scripts/`、`packaging/`**：打包与本地安装（见第 7 节）。

一条硬规则：**三者之间只有 HTTP，没有共享内存**。前端要原生能力就走 Tauri 命令，原生要问 DSH 就走 HTTP 到桥，桥再去问 DSH 宿主。

## 2. 一次对话怎么跑

1. 你在输入框打字 → 前端 `src/chat/` 的适配器把内容交给原生；
2. 原生把请求发给**当前主体的端点**（默认 `127.0.0.1:<端口>`）上的桥；
3. 桥调用 DSH 的会话接口，把这一轮交给宿主，并通过 **SSE** 把过程事件推回来；
4. 前端把 SSE 事件投影成气泡、工具卡、状态灯。

桥对外声明的能力（直接读 `/api/wallpaper/v1/status` 就能看到）：

```
status · control · sessions · history · sse · cancel · approval-handoff · resume
```

`/status` 同时也是**探测手段**：壁纸用"它答不答、答的是什么"判断这个端口上有没有可用的桥（而不是猜）。

## 3. 主体（subject）：壁纸"连谁"的三类

这是本项目最容易绕晕的地方，也是最值得先读懂的模型。

| 类别 | id 长什么样 | 身份是什么 | 端口 |
|---|---|---|---|
| 自带检出的客户端（壳） | `shell:com.deepseek.dsh` | **AUMID** | 19387（编译在它自己的包里） |
| 源码目录（检出） | 目录路径本身，如 `D:\...\deepseek-harness` | **路径** | 3080（DSH 自己的默认值） |
| 已安装的 CLI | `cli:C:\Users\...\npm\dsh.cmd` | **启动器文件** | 3080 |

三条不可动摇的规则：

1. **不替换**：主体没起来，就报"没起来"，绝不自动改用另一个主体的端点。（前端 `connect/endpoints.ts` 的 `selectEndpoint` / 原生 `lib.rs` 的 `candidates_of` 各是一半，两侧都有测试钉住。）
2. **端口不是契约**：19387 / 3080 只是默认值，用户或客户端都可以改。
3. **路径/启动器就是身份**：所以"壳"按 AUMID 寻址（重装客户端不失效），而检出按路径寻址（换目录就是换主体）。

具体落在这些文件：

- `wallpaper/src/connect/endpoints.ts`：主体 → 允许探测哪些端口、主体属于哪种形状、候选如何排序；以及"档案里存着一个已不受支持的主体时怎么办"（落回官方客户端并说明）。
- `wallpaper/src/connect/harnessSubjects.ts`：设置界面里**怎么说人话**（"客户端 / 源码目录 / 已安装的 CLI"）。
- `wallpaper/src-tauri/src/harness_targets.rs`：扫描本机有哪些主体（壳按 AUMID、检出按目录指纹、CLI 按 npm 全局目录与 PATH）。
- `wallpaper/src-tauri/src/harness_launch.rs`：把"选中的主体"变成"真的跑起来的东西"（见第 5 节）。
- `wallpaper/src-tauri/src/client_window.rs`：找出某个端点的窗口并拉到前台。

## 4. 会话：按"助手日"，一天一条

- 会话 id 形如 `wallpaper-2026-09-28`，**按助手日**计算，全天 04:00 为界（凌晨 3 点算前一天）。
- 同一条逻辑在**两处各写一遍**：`wallpaper/src/settings/store.ts` 与 `bridge/src/index.ts`。两份必须逐字一致，测试盯着这一点。
- 会话文件落在 `~/.dsh/sessions/<工作区>/<会话 id>/session.v4.jsonl.zstd`，**所有宿主共用这一个目录**，但同一条会话**同一时刻只允许一个宿主写**（DSH 的保护，报错形如 `already owned by an active write handle`）。
- 跨天要记住的东西**不靠会话继承**，靠工作区里的 `项目记忆.md`：每次新建会话时读进来注入简报（`bridge/src/index.ts` 的 `desktopEntryPrompt`）。

由此产生两条实践规则：

1. 换宿主就**新开对话**，不要让第二个宿主去 resume 第一条；
2. "会话列表"是**某一刻的快照**，不是实时查询——新出现的会话可能不在列表里，而"看不到"不等于"不存在"。

## 5. 启动一个主体：三件必须记住的事（都是实测踩出来的）

1. **npm 在 Windows 上装出来的是 `.cmd` 批处理**，`CreateProcess` 不能直接执行它，必须 `cmd /c`；
2. **控制台窗口的取舍正好相反**：
   - 启动 DSH CLI 要 **`CREATE_NO_WINDOW`**（否则壁纸旁边会多一个黑框）；
   - 启动 TUI 要**故意让控制台可见**（"运行 TUI"就是"屏幕上出现终端"），而且用 `cmd /k` 而不是 `/c`，这样它起不来时打印的原因不会被窗口一起吞掉；
3. **`dsh web` 默认会自己打开浏览器**。所以壁纸启动 CLI 时必须带 `--no-open`：开不开浏览器是**设置里的选择**（浏览器 / 终端里的 TUI），而且开机自启时不该弹任何窗口。

这些判断都在 `harness_launch.rs` 的纯函数里（`installed_cli_command`、`tui_launch_command`），因此可以用测试读回命令行，不需要真的启动进程。

启动/打开的两条入口：

- 设置里与壁纸上的「打开」→ 原生命令 `ensure_harness_ui` / `launch_harness_target`；
- TUI 路线 → 原生命令 `open_subject_tui`（**只有设置窗口能调**，找不到 TUI 时返回一句"怎么装"而不是改开浏览器）。

## 6. 从哪儿读起：三条路线

**想改"壁纸问 DSH 什么"** → `bridge/src/index.ts`（路由）、`bridge/src/protocol.ts`（事件与版本）、`bridge/tests/routes.spec.ts`（契约）。注意：桥是**以拷贝形式**装进档案的，改完源码要重建并同步到档案，且**宿主重启后**才生效。

**想改界面** → `wallpaper/src/App.tsx`（主壳与岛）、`wallpaper/src/features/`（视觉）、`wallpaper/src/settings/SettingsPanel.tsx`（设置项与文案）、`wallpaper/src/connect/`（主体与端点）。

**想改原生** → `wallpaper/src-tauri/src/lib.rs`（Tauri 命令的总入口，也是权限门所在）、`harness_targets.rs`（扫描）、`harness_launch.rs`（启动）、`client_window.rs`（窗口）、`chat.rs`（与桥的 HTTP 往返）。

读原生代码时记住一件事：**命令不是谁都能调**。形如 `require_settings(&caller)` / `require_wallpaper_surface(&caller)` 的门在每个命令开头，且还需要 `capabilities/*.json` 里列出的权限（`build.rs` 里有一份 codegen 白名单）。**只加命令不加权限 = 从界面调不到。**

## 7. 怎么跑、怎么验

```powershell
pnpm -C wallpaper typecheck          # 渲染层类型检查
pnpm test                            # 渲染层 + 桥的全部单测
cd wallpaper\src-tauri; cargo test --lib   # 原生单测（含若干"真机"测试，默认 ignore）

# 打包并安装到本机（自带 Rust 门禁、签名、安装、拉起）
pwsh -NoProfile -File .\scripts\publish-local-msix.ps1 -PackageVersion 0.2.0.145
```

两条容易忽略的注意事项：

- **拷贝依赖不会热重载插件**：桥装进档案的是一份拷贝，源码改了要么重建后同步，要么让依赖版本变化；否则"看着改了其实没生效"。
- **版本号是构建期烙进产物的**：`/status` 里的 `bridgeVersion` 来自构建时的 `package.json`，所以它不能用来判断"线上跑的是不是最新代码"，除非你确认重构建过。

## 8. 陷阱清单（都是这座机器上真实踩过的）

| 现象 | 真正的原因 |
|---|---|
| 所有会话都被判成"已归档" | 读会话快照时取错了字段（取 `id` 而不是 `header.id`），空集被当成"全归档" |
| 改完代码"没生效" | 依赖是拷贝、宿主没重启、或版本号是旧构建烙进去的 |
| "杀了进程"其实没杀掉 | 只杀了 `cmd.exe` 外壳，真正的 `node` 子进程成了孤儿（要按命令行核实、直接杀目标 pid） |
| 中文写进文件变成乱码 | 用 pwsh 拼字符串写文件；中文改动必须走编辑工具，逐文件改 |
| PowerShell 脚本莫名语法错误 | 字符串里混入了中文弯引号（PowerShell 会把它当引号） |
| 备份目录暴涨几十 GB | `robocopy` 默认跟随 junction，而 pnpm 的 `node_modules` 是链接农场；必须带 `/XJ` 并排除 `node_modules`/`.pnpm` |
| 设置里选的主体"看起来在线却连不上" | 该档案里没装桥；端口在听不代表桥在答（用 `/status` 判定） |

## 9. 有意留下、还没做的事

1. **浏览器路要求桥在该档案里**：选了 CLI 主体时，`web` 档案必须装过桥，否则壁纸看得见端口、认不出它。目前是"如实说明"，没有自动装。
2. **"让壁纸真的用 TUI 当宿主"（方案 B）没有做**：TUI 跑在自己的档案里，壁纸看不见它；要做成"同一场对话两处显示"，需要给该档案装桥并让它能被壁纸发现（并且要接受"终端关掉壁纸就离线"这个耦合）。
3. **非壳主体的窗口判定偏宽松**：`harness_launch.rs` 的 `reveal()` 对非壳主体只探测一次窗口，命中就按"它有窗口"处理。若那个端口上碰巧有别家的窗口，就可能误判——这是已知的、待收紧的地方。
