# 代码结构约定

本文供后续实现者 agent 在规划和修改代码时参考。拆分前先确认职责边界、现有调用方和测试入口，再按小批次迁移。

## 文件大小

单个源文件超过 1,500 行时（测试文件除外），先提出拆分方案，再向其中添加新功能。拆分方案应说明模块边界、迁移范围和受影响的调用方与测试。

## 模块边界

新增功能默认新建模块。只有在修改已有行为、维护模块入口或接入共享状态时，才改动已有文件；保持入口文件负责组装，领域实现放在对应模块中。

## 冻结功能

冻结功能的源码和对应测试应保留，迁到仓库根目录的 `archive/`，并断开现役入口。不要直接删除源码，也不要只靠 Git tag 留档。现役代码不得引用 `archive/`；归档目录应通过 `README.md` 说明内容和恢复方式。冻结某个功能不等于其所在模块及共享能力都不再使用。

## 注释

注释解释代码现在为什么这样设计，不记录修改历史或已经过时的实现过程。历史背景放在提交信息和项目文档中。

## Rust `unsafe`

Rust 新增的 `unsafe` 只能放在 `wallpaper/src-tauri/src/win32/` 下，并在相关 `unsafe` 块前写 `// SAFETY:`，说明调用成立的具体前提，例如句柄有效性、缓冲区长度、指针生命周期和调用线程。无法确认前提时先停下来核实，不要猜测或补空泛说明。

## 换行与编码

编辑前运行 `git ls-files --eol <文件>`，分别确认索引和工作区的行尾。Windows 的 `core.autocrlf=true` 会让索引中的 LF 在工作区显示为 CRLF；保留目标文件现有的工作区行尾，不对整个文件或目录做统一格式化。混合行尾文件必须逐行保留。新文件遵循同目录现有文件的编码和行尾。
